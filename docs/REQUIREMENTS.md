# Open LangGraph Studio — требования

Статус: черновик v1, к обсуждению.
Основание: `RESEARCH.md` (разбор API и документации, проверено на живом сервере).

## 1. Цель

Открытая замена LangSmith Studio: React-интерфейс, который поднимается **на том же порту,
что и локальный Agent Server**, и доступен по пути `/studio`.

```
langgraph dev  →  http://127.0.0.1:2024/studio      ← весь UI здесь
                  http://127.0.0.1:2024/assistants  ← API там же, тот же origin
```

Никакого `?baseUrl=`, никакого облака, никакого логина, никакого cross-origin.

### 1.1 Что решаем

Штатный Studio живёт на `smith.langchain.com` и ходит к вашему серверу через `?baseUrl=`.
Это порождает три проблемы, воспроизведённые в ходе исследования:

| Проблема | Проявление |
|---|---|
| Cross-origin | Браузер блокирует `https://smith.langchain.com` → `http://127.0.0.1:2024`: `Failed to fetch` даже при `ALLOW_PRIVATE_NETWORK=true` |
| Обязательный облачный аккаунт | Без входа в LangSmith — `403 Forbidden` |
| Allowlist доменов | При обходе через `--tunnel` домен туннеля отвергается: *«domain … is not allowed»* |

Same-origin архитектура снимает все три разом.

## 2. Архитектура

### 2.1 Основной режим — монтирование в Agent Server (по умолчанию)

Пакет отдаёт готовое Starlette-приложение, которое подключается штатным механизмом
`http.app` из `langgraph.json`:

```json
{
  "dependencies": ["."],
  "graphs": { "agent": "./agent.py:graph" },
  "http": { "app": "langgraph_studio_oss:app" }
}
```

`langgraph dev` — и UI доступен на `http://127.0.0.1:2024/studio`.

```
┌─ Agent Server, порт 2024 ────────────────────────────┐
│  /ok /metrics /docs /openapi.json   (мета)           │
│  /studio          ← НАШ SPA         (user routes)    │
│  /studio/assets/* ← НАША статика                     │
│  /assistants /threads /runs /store  (штатный API)    │
└──────────────────────────────────────────────────────┘
         ▲
         └── браузер: один origin, относительные пути
```

**Проверено на живом сервере:** `/studio` → `200`, `/studio/static/*` → `200`,
`/assistants/search` → `200`, `/docs` → `200`; SPA успешно вызвал
`fetch('../assistants/search')` **без CORS**.

Порядок маршрутов в `langgraph_api/server.py` гарантирует, что пользовательские маршруты
идут раньше API и не конфликтуют с ним (подробности в `RESEARCH.md`, §2).

Если у пользователя **уже есть** свой `http.app`, пакет даёт функцию-обёртку:

```python
from langgraph_studio_oss import mount_studio
from my_app import app          # ваш FastAPI/Starlette
mount_studio(app)               # добавляет /studio, ничего не ломая
```

### 2.2 Запасной режим — отдельный процесс с обратным проксированием

Для случаев, когда `langgraph.json` править нельзя (чужой репозиторий, прод-сервер,
удалённый деплой):

```bash
langgraph-studio-oss --target http://127.0.0.1:2024 --port 8100
# → http://127.0.0.1:8100/studio
```

Свой Starlette-сервер отдаёт SPA **и проксирует API на том же origin**, поэтому
cross-origin по-прежнему нет:

```
браузер → http://127.0.0.1:8100/studio        (SPA)
браузер → http://127.0.0.1:8100/assistants    (прокси) → http://127.0.0.1:2024/assistants
```

Требования к прокси:
- SSE проходит **без буферизации** (потоковая передача чанков, без `Content-Length`);
- проброс заголовков пагинации `x-pagination-total`, `x-pagination-next`, `content-location`;
- корректная отмена запроса при разрыве соединения клиентом (чтобы `cancel` работал);
- таймаут на стрим-эндпоинты — отключён/бесконечный.

### 2.3 Что фронт использует как транспорт

Фронт работает с API **напрямую** через `@langchain/langgraph-sdk` (MIT), сконфигурированный
на относительный базовый путь. Собственная серверная прослойка для проксирования данных
**не нужна** и не создаётся: любой лишний слой пришлось бы синхронизировать с изменениями API.

Python-часть отвечает только за: отдачу статики, конфигурацию, CLI и (в режиме 2.2) проксирование.

## 3. Ключевые решения

| Решение | Обоснование |
|---|---|
| Весь фронт пишем сами | Код ниоткуда не заимствуем — ни из Studio, ни из VizLang. Чужие открытые проекты используем как источник инженерных уроков, не более: разбор — [`VIZLANG-NOTES.md`](VIZLANG-NOTES.md) |
| Транспорт — `@langchain/langgraph-sdk` | Официальный MIT-пакет, хук `useStream` уже умеет SSE, треды, ветвление, прерывания |
| `agent-chat-ui` — только как референс chat mode | MIT, Next.js + Tailwind + shadcn/ui, но графы не рисует |
| Стек фронта: React + TypeScript + Vite | Vite даёт статическую сборку, которую Python-пакет отдаёт как файлы. Next.js не подходит: требует Node-рантайм. **Тот же стек независимо выбрал Vizlang** — это его подтверждает |
| Сборка кладётся в колесо | `pip install langgraph-studio-oss` — и всё работает, Node на машине пользователя не нужен |
| Граф рисуем на React Flow | Де-факто стандарт, MIT; даёт панораму/зум/автолейаут |
| Автолейаут — dagre/elk | Иерархическая раскладка сверху вниз, как в Studio |

### Осознанно вне области

Это функции облачного LangSmith, у локального сервера для них нет API:
**Run experiment** над датасетами, **Add to Dataset**, **View LLM Runs** / Playground,
клонирование удалённых трейсов, **Deploy** в LangSmith Cloud, **Open in VSCode**,
а также **вкладка Trace** — проверено: без `LANGSMITH_API_KEY` она показывает «No runs found».

Из видеогайда видно, как эти функции работают в облаке: `View LLM run` открывает Playground с
правкой промпта и сменой провайдера/модели, а `Run in Studio` → `Clone thread locally` копирует
продовый тред в локальный сервер. Обе цепочки завязаны на LangSmith и локально невоспроизводимы.
В UI их либо нет, либо они помечены как недоступные локально. При наличии
`LANGSMITH_API_KEY` часть из них можно добавить позже отдельным этапом.

## 5. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR.1 | **Один origin.** Фронт обращается к API только относительными путями. CORS-запросов из UI не возникает ни в одном режиме |
| NFR.2 | **Без облака.** Ни аккаунта, ни сети наружу. Работает офлайн |
| NFR.3 | **Без Node у пользователя.** В колесо кладётся собранная статика |
| NFR.4 | Поддержка Python 3.11+ (нижняя граница in-memory сервера) |
| NFR.5 | Совместимость с `langgraph-api` 0.14+; версия API проверяется через `/info`, при несовпадении — предупреждение, а не падение |
| NFR.6 | Работает и с in-memory (`langgraph dev`), и с Postgres-деплоем |
| NFR.7 | Не ломает штатные маршруты: `/docs`, `/openapi.json`, `/metrics`, `/ok` остаются доступны (проверено) |
| NFR.8 | Graceful degradation: нет `/store` — раздел скрыт; нет crons — вкладки нет; ориентир — флаги из `/info` |
| NFR.9 | Первая отрисовка < 1 c на локальной машине; бандл < 2 МБ gzip |
| NFR.10 | Устойчивость к обрыву SSE: переподключение через `GET /threads/{id}/runs/{run_id}/stream` |
| NFR.11 | Ошибки API показываются пользователю с телом ответа, а не «что-то пошло не так» |
| NFR.12 | **Совместимость с hot reload.** `langgraph dev` перезапускает граф при правке кода; UI должен переподхватывать схемы и структуру графа без перезагрузки вкладки (в видеогайде это заявлено как ключевой сценарий работы) |

### 6.1 Раскладка

```
┌───────────────────────────────┬──────────────────────────────┐
│ [◫] [граф ▾]      [Interrupts]│ New Thread ▾    [Pretty|JSON]│
│                               │                              │
│         ГРАФ (React Flow)     │      ЛОГ ТРЕДА               │
│                               │                              │
│ ┌───────────────────────────┐ │                              │
│ │ Input                  ⌄  │ │                              │
│ │  Messages    [Optional] ⌄ │ │                              │
│ │  + Message                │ │                              │
│ ├───────────────────────────┤ │                              │
│ │ [⚙ Configurable] [▶ Submit]│ │                              │
│ └───────────────────────────┘ │                              │
├───────────────────────────────┴──────────────────────────────┤
│ ● Online  http://localhost:2024        Deploy Configure Logs │
└──────────────────────────────────────────────────────────────┘
```

- Слева — граф и панель ввода, справа — лог треда, снизу — строка статуса.
- Разделитель панелей перетаскивается; левая панель сворачивается кнопкой слева вверху.

### 6.2 Оформление узлов графа (с эталонного скриншота)

Уточнено по живым референсам (`docs/references/`), а не по одному скриншоту:

| Узел | Вид |
|---|---|
| `__start__`, `__end__` | Сильно скруглённые («таблетка»), **серая** рамка и заливка |
| Обычный узел (`agent`) | Скруглённый прямоугольник ≈8 px, фиолетовая рамка, тёмно-фиолетовая заливка, точка-хэндл справа сверху |
| Узел-инструмент (`action`) | Голубая рамка, тёмно-синяя заливка |
| Активный (выполняется) | Спиннер внутри узла + подсветка рамки |
| Ошибка / прерывание | Отдельные состояния рамки (`error`, `interrupted`) |
| Обычное ребро | Сплошная линия со стрелкой |
| Условное ребро | **Пунктир** + подпись (`continue`, `end`) |

Измерено: радиус обычного узла **6 px**, служебных — `9999px` (таблетка); padding 8 px;
шрифт 14 px / 500; ширина адаптивная при высоте 32 px. Цвет узла задаёт и рамку (сплошной тон),
и фон (тот же тон с alpha 0.1), и текст (осветлённый), и исходящие рёбра (alpha 0.8).
Условные рёбра — `stroke-dasharray: 3px 1px`. Подробности в [`DESIGN-TOKENS.md`](DESIGN-TOKENS.md).

### 6.3 Общий стиль

- Тёмный фон (почти чёрный, слегка синеватый), панели — на тон светлее, тонкие разделители.
- Акцент — синий для главных кнопок (**Submit**, **Connect**).
- Шрифт интерфейса — системный / Inter; JSON и значения — моноширинный.
- Поля ввода: скругление ≈ 6–8 px, тонкая рамка, заметное кольцо фокуса.
- Иконки — тонкие штриховые (Lucide).
- Светлая тема — обязательный второй вариант (NFR.5 → FR-X.5).

> Палитра **уже снята** — не пипеткой по скриншотам, а через вычисленные стили живого Studio:
> [`DESIGN-TOKENS.md`](DESIGN-TOKENS.md) и полный дамп 481 переменной в
> `references/studio-tokens.json`. Этап E4 сводится к применению измеренных значений,
> а не к подбору.

Сборка: `pnpm build` в `frontend/` → `tsc -b && vite build` → `src/langgraph_studio_oss/static/`
→ попадает в wheel (Node на машине пользователя не нужен). База ассетов относительная
(`base: "./"`), поэтому путь монтирования меняется на стороне сервера без пересборки;
состояние интерфейса живёт в query-параметрах (`?assistantId=…&mode=…`), а не во вложенных путях.

**Взаимодействие с сервером ведёт официальный хук `useStream`** из
`@langchain/langgraph-sdk/react`: создание треда, запуск, разбор SSE, значения состояния,
история контрольных точек, ветки, прерывания, переподключение к незавершённому прогону.
Свой код поверх него — только то, что рисуется: лог и подсветка узлов
(`onTaskEvent`, `onCheckpointEvent`). Режимы потока — `values`, `tasks`, `checkpoints`.

**Объекты узлов React Flow нельзя пересоздавать на каждое событие потока.** К ним привязаны
измеренные размеры и положение хэндлов; при пересоздании они теряются, и рёбра пропадают
с холста (`getEdgePosition` возвращает null). Поэтому узлы и рёбра строятся только при смене
графа или темы, а состояние прогона они читают из стора сами.

**Узлы графа перетаскиваются.** Позиции сохраняются при перерисовке, четвёртая кнопка панели
зума (`Reset layout to default`) возвращает автораскладку.

**Версия dagre закреплена на 1.1.x.** Координаты узлов совпадают с эталоном до четверти
пикселя только в ней (0.8.5 и 1.1.x дают одинаковый результат, 2.x и 3.x — другой порядок
узлов). Обратные рёбра dagre разворачивает сам; ручной разворот уводит раскладку от эталона.

## 7.1 Ошибки выполнения

Сбой узла — рабочая ситуация при отладке графа, и обходиться с ней надо так же, как в эталоне.

1. **На холсте.** Узел, на котором встали, остаётся подсвеченным, остальные гаснут (10 %),
   рёбра — до 20 %. Справа от узла появляется бейдж `Error`.
2. **В логе.** Под записью узла — красная плашка: метка `Error`, текст исключения в одну
   строку с многоточием, кнопки `Copy error` и `Show full error message` (разворачивает
   полный текст).
3. **Продолжение.** Под плашкой — кнопка `Continue` и чип узла, с которого продолжится
   выполнение (`next` последней контрольной точки). Запуск без ввода (`submit(null)`)
   повторяет сорвавшийся шаг на том же треде.
4. **Источники.** Ошибка узла приходит в `tasks[].error` (и сохраняется в истории треда),
   ошибка прогона — событием `error` потока. Ошибка разбора формы ввода к логу не относится
   и показывается в подвале карточки `Input`.
5. **Правка состояния перед продолжением**: выбор `As Node` рядом с `Submit` позволяет
   записать значения от имени узла (`POST /threads/{id}/state` с `as_node`) и затем
   продолжить — этим же механизмом чинится и прерывание (см. 7.2).
6. **В сводке хода** (нижнее положение слайдера): вместо `Output` — `Error:` с текстом
   исключения и круглой иконкой, ниже строка `Execution paused. Review to continue.`
   с кнопкой `Review`, раскрывающей этот ход подробно.

## 7.2 Прерывания

Измерено на живом Studio; расхождения с интуицией отмечены отдельно.

1. **Меню `Interrupts`.** Строка на узел с флажками `Before` / `After`; ширина по
   содержимому (`min-width: 160px`), строка 42 px, нижний пункт — `Interrupt on all`,
   а как только хоть одна пауза включена, он превращается в `Clear all` и снимает все.
   Число включённых пауз стоит на самой кнопке `Interrupts`.
2. **Штриховка узла** помечает не паузу треда, а сам факт включённого прерывания: она
   появляется сразу при выборе `Before`/`After` и держится, пока пауза не снята.
   Диагональ 45°, шаг 10 px, цвет — тон текста узла с alpha 0.15, `mix-blend-mode: hard-light`,
   нижняя половина узла со скруглением нижних углов.
3. **На паузе холст не гаснет**: узлы и рёбра остаются в полную силу (в отличие от прогона
   и ошибки). Приглушение — признак работы или срыва, а не остановки.
4. **`Continue`** появляется под последней записью хода — и после ошибки, и на статическом
   прерывании; ответ на динамический `interrupt()` кнопкой не продолжают, там форма ответа.
5. **`As Node` рядом с `Submit`.** Пока тред стоит, вместо стрелки «More options» рядом с
   `Submit` показывается подпись `As Node` и селект узла (по умолчанию — первый из `next`).
   Нажатие `Submit` записывает введённое как результат этого узла
   (`POST /threads/{id}/state` с `as_node` и `checkpoint_id` головы) и сразу продолжает прогон.
6. **Динамический `interrupt()`** рисуется плашкой в брендовых цветах с деревом значения
   (ключи по алфавиту, значение под ключом) и формой ответа: заголовок
   «Provide a value to resume execution for {узел}», `Interrupt ID:` с копированием,
   редактор и полоса `YAML ▾ … RAW ⧉` с кнопкой `Resume` в конце.
   Ответ уходит как `Command(resume=…)`; форма показывается только у последней точки треда.
7. **Запуск** несёт `interrupt_before` / `interrupt_after` и при продолжении — эталон
   передаёт их и в `Continue`. Остальные поля запуска: `stream_subgraphs: true`,
   `multitask_strategy: "rollback"`, `stream_resumable: true`.

## 7.3 Ассистенты и конфигурация

1. **`Manage Assistants`** — модалка 960×640, колонки `2fr / 5fr`: слева список ассистентов
   текущего графа, справа их настройки. Ассистент, созданный сервером по коду графа
   (`metadata.created_by = "system"`), показывается как `Default Configuration`:
   его правка предлагается кнопкой `Create New Assistant`, а не сохранением поверх.
2. **Поля** берутся из `config_schema`: подпись — `title`, ниже описание, справа —
   аватары узлов из `langgraph_nodes` («Used in node:»). Поле с
   `langgraph_type: "prompt"` получает многострочный редактор. Ниже формы —
   `Recursion limit` и `Tags`.
3. **Версии.** Правка ассистента создаёт новую версию (`PATCH /assistants/{id}`);
   рядом с именем стоит выбор версии, откат — `POST /assistants/{id}/latest`.
4. **Активный ассистент** выбирается переключателем `Active` (и кликом по строке списка);
   с ним же связаны тред и лог — при смене всё начинается заново.
5. **Шестерёнка на узле** открывает окно 896 px «{узел} Configuration» с полями только
   этого узла; `Save` у собственного ассистента создаёт версию, у `Default Configuration`
   значения уходят в конфигурацию ближайших запусков. Внизу — ссылка
   `View full assistant settings`, открывающая модалку целиком.
6. **Выбор графа** — панель 215 px `Select a graph` в шапке: перечисляет `graph_id`
   всех ассистентов сервера и открывает системного ассистента выбранного графа.
7. **Запуск** несёт `config.configurable` со значениями формы и `recursion_limit` —
   ровно как в эталоне.

## 7.4 Chat mode

1. **Доступность.** Вкладка активна, когда во входной схеме есть `messages`, элементы
   которого типизированы сообщениями LangChain (в схеме встречаются ссылки на
   `AIMessage`, `HumanMessage` и прочие). Список `Annotated[list, add_messages]` без
   типов такой ссылки не даёт — вкладка остаётся неактивной, как и в эталоне.
2. **Раскладка.** Режим занимает всё окно: одна шапка (в ней подпись
   «`<ассистент>` (`<граф>`)»), под ней лента и поле ввода, справа — панель `Threads`
   шириной 250 px с кнопками `New` и закрытия. Лента — колонка до 1000 px с отступами
   и промежутком 48 px; сама реплика не шире 800 px.
3. **Сообщения.** Карточка с шапкой (`px-4 py-3`) и текстом под `border-t`. Реплика
   человека — рамка 2 px брендового цвета, заливка 10 %, прижата вправо и растянута
   по содержимому; остальные — обычная рамка на всю ширину ленты. Вызовы инструментов
   показываются под текстом, а служебные сообщения инструментов прячутся, пока выключен
   переключатель `Show tool calls`.
4. **Отправка.** Enter отправляет, Shift+Enter переносит строку; сообщение уходит запуском
   с `input.messages = [{type: "human", content: …}]`. Поток дополнительно включает
   режим `messages`, поэтому ответ модели печатается по мере генерации.
5. **Подпись треда** в панели — первое сообщение человека; список перечитывается, когда
   прогон закончился.

## 7.5 Store и запасной режим

1. **`Memory`** открывает окно во всю ширину с отступом: слева список записей Store
   (ключ и путь пространства имён) и кнопка `Add new item`, справа — форма
   `Key` / `Namespace` / `Value` с редактором YAML/JSON, кнопками `Reset`, `Save`
   и `Delete` у сохранённой записи. Пространство имён вводится путём через `/`,
   пустое поле означает корень.
2. **`Cancel all pending runs`** внизу списка тредов: подтверждение, затем обход
   занятых тредов (`status: "busy"`) с отменой их незавершённых прогонов.
3. **Запасной режим** (2.2): `langgraph-studio-oss --target … --port …` поднимает
   свой процесс с интерфейсом и обратным прокси. Прокси переносит заголовки, кроме
   hop-by-hop и `content-length`, отдаёт SSE кусками без буферизации и закрывает
   поток вместе с соединением клиента.

## 7.6 Наведение и подграфы

1. **Карточка узла.** Наведение на узел через 330 мс открывает панель справа от него
   (шириной по содержимому, не больше 300 px): имя чипом, строки `Source` и `Target`
   с чипами соседей и — через разделитель — флажки `Interrupt Before` / `Interrupt After`.
   Прерывание ставится прямо отсюда, счётчик у кнопки `Interrupts` и штриховка узла
   меняются сразу. Служебные `__start__` / `__end__` карточки не имеют.
2. **Подсветка из лога.** Наведение на запись узла в правой панели подсвечивает его
   на холсте (масштаб 1.05) и гасит остальные до 30 % — это отдельный уровень от прогона,
   где неактивные узлы гаснут до 10 %. Строка контрольной точки ничего не подсвечивает.
3. **Подграфы свёрнуты по умолчанию**: узел-подграф выглядит обычным, но со значком слева
   (при наведении значок меняется на «развернуть») и курсором-указателем.
4. **Раскрытие** — клик по узлу или пункт `Show subgraph nodes` в его карточке. Вложенные
   узлы приходят от сервера как `<подграф>:<узел>` (`GET /assistants/{id}/graph?xray=true`),
   показываются с короткими именами и своими тонами, а вокруг них рисуется рамка подграфа.
   Свернуть — клик по рамке или `Hide subgraph nodes`.
5. **Раскладка пересчитывается целиком**: ряды раздвигаются на 25 px сверху и снизу
   рамки, поэтому соседние узлы не накладываются. Сохранённые вручную позиции при этом
   сбрасываются — иначе узлы остались бы на местах свёрнутой картинки.
6. **Рамка перетаскивается вместе с содержимым**, а вложенный узел не может выйти
   за её пределы (`parentId` + `extent: "parent"` в React Flow).
7. **Холст двигается прокруткой**, а не перетаскиванием фона: иначе слой `pane`
   перехватывает клики по рамке подграфа, которая лежит под узлами.
8. **Карточка вложенного узла** показывает короткое имя и соседей, но без флажков
   прерываний: пауза внутри подграфа не ставится.
9. **Подсветка подграфа целиком.** Наведение на запись `worker` в логе оставляет яркими
   и рамку, и её вложенные узлы (последние ещё и увеличиваются), остальное гаснет до 30 %.
10. **Запись подграфа в логе** отличается от обычной: аватар квадратный (радиус 4) со
    значком подграфа вместо буквы, справа от имени — кнопка «развернуть», видимая при
    наведении на строку (клик раскрывает подграф на холсте). Внутри записи, когда она
    раскрыта, показывается **вложенный лог подграфа**: его контрольные точки и узлы
    со своими аватарами. Историю шагов отдаёт тот же `POST /threads/{id}/history`,
    но с `checkpoint.checkpoint_ns` из задачи (`<узел>:<id задачи>`); ответ идёт
    от новых к старым, поэтому его переворачивают. Липкие заголовки вложены ступенькой:
    родитель на `top: 46px`, подграф — на `70px`.
11. **Ручные позиции переживают перестроение.** Узлы, которые двигал пользователь,
    остаются на своих местах при раскрытии подграфа, смене темы и перерисовке по ходу
    прогона; всё остальное встаёт по автораскладке. `Reset layout to default` очищает
    запомненные позиции.

## 7.7 Сверка с эталоном

Пять графов (`agent`, `multi`, `hitl`, `chat`, `nested`) прогоняются в обоих интерфейсах
на одном и том же треде: прогон делается у нас, затем тот же `threadId` открывается в
оригинале — данные тогда совпадают, и любая разница является разницей отображения.
Проверяются: лог на всех уровнях детализации, роли сообщений, `View state`, карточки
по наведению, подсветка узлов, подграфы, панель ввода и чат.

Из сверки выросли правила, которых не было раньше:

1. **Четыре уровня детализации** (0…3), значение хранится в `ls:studio:traceLogInfoLevel`.
   Слайдер поддерживает клик, перетаскивание, стрелки и Home/End.
2. **Значения состояния** везде рисуются одним деревом (см. токены): в логе, в сводке
   и в `View state`. Список `messages` разбирается на сообщения с ролями.
3. **Ход, который не доигран** (ошибка или пауза), подсвечивается `--bg-brand-secondary`,
   а сводка целиком кликабельна.
4. **`Re-run from here`** не показывается на стартовой точке хода; **`Edit node state`** —
   только у развёрнутой записи без ошибки.
5. **Ручные позиции узлов** хранятся в `ls:studio:<assistantId>:nodePosition`, прерывания —
   в `ls:studio:<assistantId>:interrupts`; `Reset layout to default` очищает позиции
   и сворачивает подграфы.
6. **Холст**: колесо масштабирует, вписывание — только по кнопке (`padding: 0.1`),
   раскрытие подграфа вьюпорт не трогает.
7. **Рамка подграфа** встаёт туда же, где стоял свёрнутый узел.
8. **Панель ввода**: `messages` правится конструктором сообщений (карточка на реплику,
   кнопка `Message`), числовые поля — обычным `input[type=number]`, редактор кода
   остаётся для остальных типов и для `View Raw`.
9. **Чат**: список тредов не фильтруется по графу и подгружается страницами; подпись треда —
   текст первого сообщения независимо от роли, под карточкой сообщения — `Copy` и `Edit`
   (у ответа модели — `Copy` и `Regenerate`), реплика человека прижата вправо по содержимому.
10. **Разметка лога** повторяет виртуальный список эталона: скроллер `thread-log`, внутри
   `virtuoso-scroller` с закреплённым `virtuoso-top-item-list` (заголовок текущего хода)
   и `virtuoso-item-list`, где каждая строка — отдельный элемент. Заголовки следующих ходов
   липкие и наезжают на закреплённый.
11. **Уровень 1** раскрывает ровно две записи: ввод (`__start__`) и последнюю запись хода.
   Уровень 0 показывает сводку теми же значениями, что и запись узла, но без пузыря.
12. **`View state`** прижат к правому краю окна (600 px), значения и сообщения в нём раскрыты.
13. **Подсказки** — собственный компонент (700 мс, 14px, `p-2`, радиус 6), только там, где
   они есть у эталона: выбор графа и треда, слайдер детализации, состояние подключения,
   `Run experiment`.
14. **Память** показывает дерево пространств имён с числом записей и подписью времени
   по-английски; записи подгружаются на раскрытии узла.

## 8. Этапы

| Этап | Содержание | Итог |

| **E0** ✓ | Каркас пакета, `http.app`, отдача статики, `/info` в подвале | `/studio` открывается на 2024 |

| **E9** ✓ | Store, режим прокси (2.2), упаковка и релиз | Готово к публикации |

## 9. Риски

| Риск | Смягчение |
|---|---|
| API меняется между версиями `langgraph-api` | Проверять `/info`; держать матрицу совместимости в CI; при расхождении — предупреждать, а не падать |
| Конфликт с существующим `http.app` пользователя | `mount_studio(app)` + понятная ошибка при коллизии пути; путь настраивается |
| Точное совпадение визуала | Отдельный этап E4 со снятием референсов; сначала функциональность |
| Юридическая чистота | Не копируем код и ассеты Studio. Воспроизводим внешний вид по публичным материалам, всё пишем сами. Название и иконки — свои |
| Раздувание объёма | Явно вынесли облачные функции за границы (§4, «вне области») |

## 10. Принятые решения

| Вопрос | Решение |
|---|---|
| **Имя пакета** | `langgraph-studio-oss` на PyPI, модуль `langgraph_studio_oss`. Имя `langgraph-studio` занято |
| **Chat mode** | Делаем, но **после** графового режима — этап E8. Сначала доводим Graph mode до паритета |
| **Memory (Store)** | **Полный CRUD**, как в Studio: просмотр, поиск, создание, правка, удаление. Приоритет P1 |
| **Светлая тема** | Обе темы сразу: токены уже сняты для обеих, разница только в значениях переменных |

## 11. Открытые вопросы

1. **Путь монтирования.** Решено: `/studio` по умолчанию, меняется параметром —
   `mount_studio(app, path="/lg-studio")` и `--path` у команды.
2. **Авторизация.** Если сервер поднят с `auth`, нужно ли UI поддерживать заголовки/токен?
   (В штатном Studio для этого есть Custom Headers.) Пока не делаем: у `langgraph dev`
   авторизации нет, а для защищённого сервера нужен продуманный ввод и хранение секрета.
3. **Crons.** Решено: интерфейса не делаем — его нет и в эталоне
   (расписания заводят через SDK или API), хотя эндпоинты локально отвечают.
